SIH Problem Statement: "AI-Based Detection of Cyber Threats in Unidirectional IP Traffic"

Problem Being Solved:
High-security enclaves—such as industrial control systems (ICS/SCADA), power grids, nuclear power plants, defense command centers, and air-gapped government infrastructure—frequently utilize hardware data diodes to establish unidirectional IP network links. A data diode physically restricts data transmission to a single direction (e.g., from an isolated operational technology enclave to an enterprise monitoring network). While this guarantees that hostile external entities cannot transmit malicious packets back into the high-security enclave, it severely complicates network security monitoring:
1. Security monitoring tools inside or outside the enclave receive only unidirectional traffic metadata.
2. Active probing, port scanning, ping sweeps, and TCP SYN handshakes are physically impossible because no return path exists.
3. Deep Packet Inspection (DPI) and TLS decryption are prohibited or impossible due to encryption, high throughput demands, and zero key-sharing policies.
4. Traditional Network Detection and Response (NDR) systems fail because they rely on bidirectional flow reconstruction, TCP session handshake tracking, active mitigation responses (TCP RST injection), and external cloud threat intelligence lookups.

Core Objective & Proposed Solution:
PassiveGuard AI is a non-intrusive, zero-emission, passive Network Detection & Response (NDR) platform explicitly engineered for unidirectional IP traffic enclaves. The system passively consumes unidirectional flow telemetry or PCAP packet feeds, extracts rich statistical and temporal feature vectors, evaluates traffic across seven independent threat detectors, fuses findings using a multi-detector risk engine and Random Forest Machine Learning (ML) classifiers trained on real cybersecurity benchmark datasets (UNSW-NB15), and broadcasts real-time security alerts to a React-based SOC dashboard over WebSockets.

Target Environment & Target Users:
- Target Environments: Critical National Infrastructure (CNI), SCADA/ICS networks, data diode enclaves, defense command enclaves, financial vault enclaves, and zero-trust air-gapped facilities.
- Target Users: Security Operations Center (SOC) analysts, Industrial Cybersecurity Engineers, Operational Technology (OT) Security Officers, and Enclave Security Administrators.

Main Technical Innovation:
PassiveGuard AI introduces a Hybrid Dual-Layer Detection Engine:
- Layer A (Behavioral & Statistical Heuristics): Computes deterministic anomaly metrics (destination fan-out, temporal inter-arrival periodicity, Shannon entropy of subdomains, packet-size variance, directional byte asymmetry).
- Layer B (Local Machine Learning Inference): Runs local RandomForestClassifier inference on normalized 12-feature vectors without invoking network sockets, cloud APIs, or active polling.
- Hybrid Fusion Engine: Merges Layer A and Layer B scores safely (Fused Score = max(Stat_Score, 0.50 * Stat_Score + 0.50 * ML_Score)), preventing ML false negatives from suppressing critical statistical security signatures while suppressing false positives through temporal cooldown deduplication.

2. PROBLEM STATEMENT ANALYSIS
--------------------------------------------------------------------------------
What is Unidirectional IP Traffic?
Unidirectional IP traffic is network communication constrained physically or logically to transmit in exactly one direction (A -> B) with zero transmission in the reverse direction (B -> A). In a data diode deployment, physical light-emitting diodes (LEDs) and photoreceivers ensure that data flows from an enclave to an external network, but photons cannot travel backwards.

What is a Passive Monitoring Enclave?
A passive monitoring enclave is an isolated computing environment where security sensors observe data streams via passive network TAPs or data diode receiver ports. The sensor possesses no physical or logical ability to inject packets, establish TCP handshakes, issue ICMP probes, resolve DNS names, or execute active countermeasures.

Why Conventional Security Systems Fail:
1. Dependency on Bidirectional TCP Handshakes: Traditional Intrusion Detection Systems track TCP state transitions (SYN -> SYN-ACK -> ACK). In unidirectional links, the monitoring sensor sees only SYN or SYN-DATA packets without corresponding SYN-ACK responses.
2. Strict Prohibition of Active Probing: Enterprise scanners emit active network probes to verify host liveliness or service versions. In unidirectional enclaves, active probing is physically impossible and security policy strictly forbids any packet emission.
3. No Return-Path Communication: The sensor cannot query cloud threat intelligence feeds (e.g., VirusTotal, AbuseIPDB) or update signature databases dynamically over HTTP/REST APIs.
4. Encrypted Payload Blindness: Modern enterprise traffic utilizes TLS 1.3 and QUIC. Without private key possession or active MITM proxying, payload inspection is impossible.

The Six Target Threat Categories in PassiveGuard AI:
1. Volumetric / Protocol DDoS: Abnormally high packet arrival rate (>10,000 pkts/sec), SYN flag dominance without ACK responses, source entropy anomalies.
2. Botnet C2 Beaconing: Periodic inter-arrival timestamps, recurring destination IP/port tuples, small uniform packet sizes.
3. DGA Domains: High Shannon entropy (H > 3.8), high digit ratio, lexical randomness in DNS query metadata.
4. DNS Tunnelling: Long subdomain query strings (>30 chars), high query frequency to single apex domain, high byte volume over UDP port 53.
5. Encrypted TLS/QUIC Malware: Fixed TLS record length distributions, suspicious JA3/JA4 fingerprint hashes, SSLv3/legacy protocol usage.
6. Reconnaissance / Port Scanning: Single source IP connecting to many distinct ports (vertical) or dest IPs (horizontal) within short temporal windows.
7. Data Exfiltration: Unidirectional byte asymmetry (Bytes_out >> Bytes_in), sustained high-volume outbound TCP transfers to rare destinations.

3. PROPOSED SOLUTION
--------------------------------------------------------------------------------
PassiveGuard AI enforces an Observation-Only Pipeline Architecture. It reads streaming network flows or PCAP files, computes statistical metrics and ML features, evaluates threat detectors, fuses risks, and persists findings to a local SQLite database for SOC display.

Pipeline Flow:
Traffic Source -> Passive Ingestion -> Feature Engine -> 7 Threat Detectors + Layer B ML Engine -> Risk Fusion Engine -> Alert Store & Cooldown -> React SOC Analyst Dashboard

Core Operating Principles:
1. Passive Observation Only: Zero packet creation, zero socket binding for network output, zero active probing.
2. Payload-Agnostic Metadata Analysis: Operates strictly on header metadata (IP, port, TCP flags, duration, packet sizes, DNS subdomain strings, TLS SNI/JA3). Zero TLS decryption required.
3. Explainable Evidence Generation: Every generated alert includes an evidence JSON dictionary explaining why the alert fired (e.g., exact Shannon entropy, fan-out count, sub-score breakdown, feature importances).

How Packets Become Flow Records:
1. Packet Capture (ObservedPacket): PCAPReader iterates through packet headers using scapy or dpkt, parsing IP addresses, ports, transport protocol, frame length, TCP flags, and microsecond timestamps.
2. Flow Aggregation (FlowAggregator): Packets sharing the 5-tuple identifier (src_ip, dst_ip, src_port, dst_port, protocol) are grouped into a streaming FlowRecord.
3. Timeout Eviction: An inactive flow is finalized and emitted to the feature pipeline when its inter-packet inactivity gap exceeds flow_timeout (default: 15.0 seconds).

8. FEATURE ENGINEERING
--------------------------------------------------------------------------------
12-Feature Vector Schema:
1. flow_duration: t_last - t_first (seconds)
2. flow_packet_count: Total packets observed in flow window
3. flow_byte_count: Total payload & header bytes
4. flow_packets_per_sec: packet_count / max(duration, 0.001)
5. flow_bytes_per_sec: byte_count / max(duration, 0.001)
6. tcp_syn_count: Total TCP packets carrying SYN flag
7. tcp_ack_count: Total TCP packets carrying ACK flag
8. tcp_syn_ack_ratio: syn_count / max(ack_count, 1)
9. directional_byte_ratio: bytes_src_to_dst / max(byte_count, 1)
10. directional_packet_ratio: pkts_src_to_dst / max(packet_count, 1)
11. packet_size_mean: byte_count / max(packet_count, 1)
12. packet_size_std: Standard deviation of packet sizes

Protocol-Specific Feature Extraction:
- DNS Subdomain Shannon Entropy (H): Calculated over DNS query labels to detect DGA domains and covert DNS tunnelling.
- TLS Metadata Features: Evaluates tls_version, SNI hostname, tls_ja3 fingerprint hash, and packet-size variance without decrypting payloads.

9. THREAT DETECTION MODULES
--------------------------------------------------------------------------------
9.1 DDoS Detector (backend/app/detection/ddos.py)
- Purpose: Detects high-volume SYN floods, UDP floods, and amplification attacks.
- Features: flow_packets_per_sec, tcp_syn_ack_ratio, directional_packet_ratio, source_entropy.
- Logic: Layer A statistical scoring combines arrival rate intensity and unanswered SYN ratios. Layer B evaluates ddos_rf_unsw_nb15_v1.joblib.
- Hybrid Score: max(Stat_Score, 0.50 * Stat_Score + 0.50 * ML_Score). Alert threshold: >= 0.60.
- Demo Status: Verified in scripts/run_demo.py --scenario ddos.

9.2 C2 Beaconing Detector (backend/app/detection/c2.py)
- Purpose: Identifies automated low-and-slow C2 heartbeats.
- Features: Inter-arrival timestamp sequence (delta_t), destination IP recurrence, TLS metadata.
- Logic: Calculates temporal periodicity index P = 1.0 - min(1.0, std(delta_t) / mean(delta_t)).
- Alert Threshold: P >= 0.75 and recurrence count >= 4. Mapped to HIGH severity.
- Demo Status: Verified in scripts/run_demo.py --scenario c2.

9.3 DGA Detector (backend/app/detection/dga.py)
- Purpose: Detects Algorithmically Generated Domains used by malware for C2 rendezvous.
- Features: domain_name, dns_entropy, dns_query_length, dns_digit_ratio, dns_unique_character_ratio.
- Logic: Evaluates Shannon entropy (H > 3.8), label length (L > 18), and digit concentration.
- Alert Threshold: Fused DGA score >= 0.65. Mapped to HIGH severity.
- Demo Status: Verified in scripts/run_demo.py --scenario dga.

9.4 DNS Tunnelling Detector (backend/app/detection/dns_tunneling.py)
- Purpose: Detects data exfiltration encoded within DNS queries.
- Features: Subdomain length, query frequency per apex domain, byte volume over UDP port 53.
- Logic: Evaluates total character volume across subdomains sharing the same parent domain.
- Alert Threshold: Subdomain length > 30 and query volume > 1000 bytes.
- Demo Status: Verified in scripts/run_demo.py --scenario dns_tunnel.

9.5 Encrypted Malware / TLS Detector (backend/app/detection/tls.py)
- Purpose: Identifies suspicious encrypted TLS/QUIC sessions without payload decryption.
- Features: tls_version, tls_ja3, tls_std_packet_size, tls_mean_packet_size.
- Logic: Flags SSLv3/TLS 1.0 usage, known malicious JA3 signatures, and near-zero packet-size variance (std < 2.0).
- Alert Threshold: Mapped to MEDIUM or HIGH severity.
- Demo Status: Verified in scripts/run_demo.py --scenario tls_malware.

9.6 Reconnaissance Detector (backend/app/detection/recon.py)
- Purpose: Detects vertical port scans, horizontal sweeps, and SYN probing.
- Features: Source IP tracking state, unique destination ports, unique target IPs, short flow ratios.
- Logic: Bounded state tracker computes port fan-out and destination fan-out sub-scores. Layer B evaluates recon_scan_rf_unsw_nb15_v1.joblib.
- Alert Threshold: Unique ports >= 3 or unique destinations >= 3 with fused score >= 0.65.
- Demo Status: Verified in scripts/run_demo.py --scenario recon.

9.7 Data Exfiltration Detector (backend/app/detection/exfiltration.py)
- Purpose: Identifies unauthorized large-scale outbound data transfers.
- Features: directional_byte_ratio, bytes_src_to_dst, bytes_dst_to_src, destination rarity.
- Logic: Flags flows where directional byte ratio > 0.95 and outbound volume > 10 MB.
- Alert Threshold: Mapped to HIGH or CRITICAL severity.
- Demo Status: Verified in scripts/run_demo.py --scenario exfiltration.

14. HYBRID DETECTION & RISK FUSION
--------------------------------------------------------------------------------
The RiskFusionEngine (backend/app/risk/fusion.py) aggregates findings from all 7 detectors:
1. Primary Threat Selection: Identifies detector with highest confidence score (S_max).
2. Multi-Detector Corroboration: Increases risk score if multiple independent detectors trigger on the same flow:
   S_fused = min(1.0, S_max + 0.10 * (N_active - 1))
3. Cooldown Suppression: Suppresses identical alerts from the same source IP within a 60-second window to prevent alert fatigue.

28. JUDGE QUESTIONS AND ANSWERS (25 TECHNICAL Q&As)
--------------------------------------------------------------------------------
1. Q: How does PassiveGuard AI work on a unidirectional data diode link?
   A: It operates in pure observation mode. It receives incoming packet metadata from the diode's receiving interface without ever writing to or transmitting over a network socket.
2. Q: How can you track TCP flows if you never see TCP ACK responses from the receiver?
   A: Our FlowAggregator groups packets into streaming flow objects based on observed 5-tuples and unidirectional time windows, tracking source-to-destination byte/packet counts without requiring completed 3-way handshakes.
3. Q: Why use Machine Learning if statistical rules already detect attacks?
   A: Statistical rules detect known behavioral bounds, while Random Forest ML captures non-linear feature interactions that rules might miss.
4. Q: How do you detect malware in encrypted TLS traffic without decrypting the payload?
   A: We evaluate handshake metadata (TLS version, cipher suites, SNI, JA3 hashes) and packet-size variance. Malicious C2 sessions frequently exhibit fixed packet size profiles.
5. Q: What dataset was used to train the ML models?
   A: The public UNSW-NB15 cybersecurity dataset captured by the Australian Centre for Cyber Security.
6. Q: Did you train and evaluate on the same data partition?
   A: No. We strictly preserved the official predefined benchmark boundary: UNSW_NB15_training-set.csv for training/validation and UNSW_NB15_testing-set.csv for held-out evaluation.
7. Q: How do you prevent data leakage during feature scaling?
   A: Our StandardScaler is fitted exclusively on the training partition. Test set feature vectors are transformed using the pre-fitted training parameters.
8. Q: Why does the DDoS demo show ML Label = BENIGN while the statistical score is HIGH?
   A: Synthetic demo flows differ slightly in feature distribution from real UNSW-NB15 DoS traffic. Our hybrid fusion algorithm ensures statistical security signatures are never suppressed by ML disagreement.
9. Q: How do you calculate DGA domain risk?
   A: We measure the Shannon entropy of query subdomain strings. Strings with entropy > 3.8 and high digit ratios are flagged.
10. Q: Can PassiveGuard AI perform active mitigation (e.g., blocking an IP address)?
    A: No. Active response is strictly prohibited in passive enclaves because returning packets across a data diode is physically impossible and security policy forbids automated disruption of critical control loops.
11. Q: How are alerts delivered to the analyst?
    A: Alerts are persisted to a local SQLite database (data/alerts.db) and broadcast asynchronously over WebSockets (ws://localhost:8000/ws/alerts) to the React dashboard.
12. Q: How does the system handle high-volume alert floods?
    A: The RiskFusionEngine enforces a 60-second temporal cooldown deduplication window per source IP and threat class.
13. Q: What happens if an ML model joblib file is missing or corrupted?
    A: The MLInferenceEngine catches loading exceptions safely, logs a warning, and falls back seamlessly to Layer A statistical detection.
14. Q: What transport protocols are supported?
    A: TCP, UDP, and ICMP IP traffic.
15. Q: How do you detect C2 beaconing?
    A: By tracking inter-arrival timestamps (delta_t) across recurring destination tuples to calculate a temporal periodicity index.
16. Q: What is the false positive rate of your DDoS model?
    A: 1.52% on the held-out UNSW-NB15 test set.
17. Q: What is the false negative rate of your Reconnaissance model?
    A: 2.00% on the held-out UNSW-NB15 test set.
18. Q: How do you verify that your code never sends network packets?
    A: We execute automated AST static analysis unit tests (pytest) that scan the codebase for socket creation or packet transmission function calls.
19. Q: Is the system scalable to 10 Gbps links?
    A: The current Python prototype processes ~6.0 events/second in single-threaded Python. Production 10 Gbps deployment would require C++/DPDK packet processing.
20. Q: Why Random Forest instead of Deep Learning / PyTorch?
    A: Random Forests provide fast CPU inference (<1.5 ms), low memory footprint, resilience against feature scaling issues, and direct feature importance explainability.
21. Q: What is JA3 fingerprinting?
    A: An MD5 hash of specific TLS Client Hello parameters (TLS version, accepted ciphers, extensions, elliptic curves) used to identify client application software.
22. Q: How is data exfiltration detected?
    A: By identifying asymmetric outbound byte transfers where Bytes_out / Bytes_total > 0.95 and total volume exceeds 10 MB.
23. Q: Can PassiveGuard AI run completely air-gapped?
    A: Yes. It relies on zero cloud APIs, zero external threat intelligence feeds, and zero internet dependencies.
24. Q: Where are alerts stored?
    A: In a local, embedded SQLite database (data/alerts.db).
25. Q: What makes this solution unique for SIH?
    A: It is purpose-built for the constraints of unidirectional IP enclaves—combining passive metadata analysis, hybrid statistical/ML fusion, and zero-emission security.
